# RQ2 implementation gap analysis

## Verified repository context

- The active experiment entry points are in `backend/app/experiments/rq2/` and their implementation is in `backend/app/src/rq2/`. There is no `rq2_privacy/` directory. The latter source package also contains serving modules imported by `backend/app/main.py`. Those modules and their existing RQ1 dependencies are outside the research refactor.
- The shipment source is `backend/app/data/raw/Suppy_Chain_Shipment_Data.csv`. RQ1's composite uses the four requested matching fields in order. Its ground truth instead groups on molecule/test type, dosage, dosage form, and pack size. The shared loader preserves this distinction. The RQ1 preparation caps each entity at 20 records.
- RQ1 normalizes the fields, joins them with a literal `|`, pads both ends of the whole string with `_`, and inserts distinct character bigrams. The insertion universe consists of those literal bigrams, including separator-crossing and padding grams. There are no explicit field tags. The index in `{index}:{gram}` distinguishes the k HMAC inputs for a single gram. Counting indexed copies as independent insertion tokens would multiply Q by k and distort the specified proxy.
- RQ1's frozen raw and normalized exact comparators use unkeyed SHA-256. The shared exact linker already accepts a key for HMAC-SHA256. RQ2's legacy experiment uses HMAC for its secondary exact metrics and unkeyed normalized SHA-256 for its primary cluster metrics.
- The frozen RQ1 research policy selects one threshold per split seed and field set across the four validation noise levels. The stored composite single thresholds at 15% range from 0.86 to 0.96 across seeds 0–9. There is no single frozen scalar cutoff. RQ1's split is 30% validation and 70% test, regenerated by entity for each seed, using the same public reproducibility key across seeds. The proposed three-way fixed split and per-seed private keys require a separate replay context to reproduce the stored rows.
- The prepared dataset and the description-only noisy files for 5%, 15% and 30% exist for seeds 0–9. Zero noise loads the prepared base. The repository also contains older flat noisy files and an optional all-fields noise profile. The frozen RQ1 workflow uses the shared prepared/noisy paths, and changes only descriptions.
- RQ3 has its own experiment entry point and a shared response-sweep implementation. Its YAML inherits from RQ2, its configuration pairs are currently static, and an RQ2 compatibility entry point still runs the response sweep. The checked-in `base.yaml` contains the public RQ1 fixture key. The RQ2 empirical threat model requires a separate environment key. Keep the fixture key for replay and keep serving configuration outside this work.

The new experiment should reuse the shared loader and truth IDs, field builder, encoder, pre-generated noise, Dice, clustering, exact linker, metric helpers, I/O and aggregation. Legacy RQ2 separately implements a cross-party threshold/metric path, repeats encoding and distance work alongside shared cluster evaluation, and contains a separate raw-CSV alias and normalization path. Reuse the shared prepared-record path for the new workflow. Retain legacy interfaces where the existing experiments, tests or serving call them. The cross-party comparisons require an explicit definition of aligned observations and eligible pairs before they can be reported consistently.

## Initial design questions and confirmed amendments

1. Replay the frozen RQ1 rows in a dedicated gate using the published fixture key, original two-way split and stored composite `single` cutoff for each seed. Run the main benchmark on one fixed three-way entity partition, with a separate environment-rooted key per noise seed, and use each corresponding RQ1 cutoff as the historical policy. Use the current encoder's literal insertion universe for both. This preserves RQ1 parity and leaves the main reference corpus entity-disjoint.
2. Use the normalized, keyed exact comparator in RQ2. It has the same equality criterion as RQ1's normalized unkeyed comparator. Use validation-only evidence to select the recommended configuration subject to the 0.05 F1 budget. Report its held-out comparison separately using the requested test metrics and report the historical RQ1 cutoff alongside the validation-selected cutoff.

The owner confirmed the separate gate and keyed exact comparator. The main benchmark regenerates a 25% validation, 45% test, and 30% reference partition for each paired seed. All Bloom cells use the same validation cutoff selection procedure. Only Baseline 2 reports the historical cutoff as a secondary comparison. See [the implemented protocol](RQ2_COLLISION.md).

## Read-only verification

The common linkage path replayed all ten frozen composite, single-cutoff rows at 15% noise with exact equality on all seven stored metric/count fields. The configured key fingerprint matched the frozen run metadata. The four top-level frozen RQ1 artifacts had identical SHA-256 hashes before and after verification. On the full seed-0 15% population of 1,855 records across 149 entities, mean Q was 45.563342, median Q was 44, and the insertion universe contained 699 distinct tokens. This is an inspection result for the frozen population. The new pipeline gate and main-cohort figures still require implementation.

The existing configured pytest suite finished with 235 passes and one skip. The skipped test requires Pyflakes, which is absent from the active environment. Pytest also reported one upstream websockets deprecation warning.
